## Why this work exists

- **Problem #1:** the links and "other specifics" a user types in the wizard are sent once to `/api/generate` and never saved.
- **Problem #2:** Studio's "regenerate" (`src/routes/-studio/Editor.tsx`, `regenerate()`) only sends `{provider, resumeUploadId, otherSpecifics: instructions}`. It loses the links, the Minimal/Bold choice (`designIntensity`) and the original specifics, so every regenerate is worse than the first generation.
- **Problem #5 (part):** free users get the clean HTML from `GET /api/content` and from the `POST /api/generate` response. The plan says free users must only ever receive a watermarked copy from the app's endpoints.

## Task A: Save the inputs (`portfolio_inputs`)

### A1. Migration `supabase/migrations/0009_portfolio_inputs.sql`
- Table `public.portfolio_inputs`:
  - `user_id uuid primary key references auth.users (id) on delete cascade`, the same as `portfolios` in `0001_init.sql`.
  - `links jsonb not null default '{}'::jsonb`, the same shape as `ProfileLinks` in `src/server/llm`.
  - `specifics text`
  - `design_intensity text not null default 'minimal' check (design_intensity in ('minimal','bold'))`
  - `updated_at timestamptz not null default now()`
- Enable row-level security, with three policies for the owner only (`auth.uid() = user_id`): select, insert and update. **No delete policy.** Copy the policy style of `portfolios` in `0001_init.sql`.
- `POST /api/reset` (`src/routes/api/reset.ts`) must also delete the user's `portfolio_inputs` row. Look at how it deletes the other rows.
- **Do not apply the migration to the remote Supabase project.** Only write the file. The owner applies it after the review.

### A2. Shared parsing
- Move `parseLinks`, `cleanString` and the `MAX_LINK_LENGTH` / `MAX_LINKS` limits out of `src/routes/api/generate.ts` into a new `src/server/portfolio-inputs.ts`, unchanged, and import them back into `generate.ts`.
- In the same file, add:
  - `loadPortfolioInputs(supabase, userId)`, which returns `{ links, specifics, designIntensity }` with safe defaults when there's no row.
  - `savePortfolioInputs(supabase, userId, partial)`, which upserts the row and sets `updated_at`.
- Cap `specifics` at 4000 characters (trim it, and treat an empty string as `null`).

### A3. Route `src/routes/api/portfolio/inputs.ts`
- `GET` → `{ links, specifics, designIntensity, updatedAt }`
- `PUT` with body `{ links?, specifics?, designIntensity? }` → validates with the shared helpers (reject a bad `designIntensity` with a 400 `invalid_request`), upserts, and returns the same shape as `GET`.
- Uses `authMiddleware`. Look at `src/routes/api/content.ts` for the pattern. The route tree file `src/routeTree.gen.ts` is regenerated by the dev server or build, so don't hand-edit it.

### A4. Wizard (`src/routes/onboarding.tsx`)
- On mount, `GET /api/portfolio/inputs` and pre-fill the links, specifics and Minimal/Bold fields if they're empty.
- When those fields change, `PUT /api/portfolio/inputs`, **debounced by about 800 ms**. Don't block the UI, and fail silently (a `console.warn` at most).
- Keep sending the same body to `/api/generate` as today. Nothing else in the wizard changes.

### A5. `/api/generate` (`src/routes/api/generate.ts`)
- Accept a new optional body field `instructions` (string, max 2000 characters).
- Resolve the inputs like this:
  - If the body contains `links`, `otherSpecifics` or `designIntensity`, **save them** with `savePortfolioInputs`, then use them.
  - For any of those three fields missing from the body, use the saved value from `loadPortfolioInputs`.
  - If `instructions` is present, pass it to the model **in addition to** the specifics. Extend `buildPortfolioHtmlUserMessage` in `src/server/llm/index.ts` with an optional `revisionInstructions` that is added as its own clearly labelled block, e.g. "Changes the user asked for in this regeneration". Don't overwrite the specifics with it.
- Don't change anything else in this route: rate limit, key handling, photo, reference images, the error codes, saving to `portfolios`.

### A6. Studio regenerate (`src/routes/-studio/Editor.tsx`)
- `regenerate()` sends `{ provider: "google", resumeUploadId, instructions }`, and **no** `otherSpecifics`. The server now fills in the saved links, specifics and Minimal/Bold.

## Task B: Server-side watermark for free users

### B1. `src/server/watermark.ts`
- `export const WATERMARK_ATTR = "data-shipfolio-watermark";`
- `export function addWatermark(html: string): string` inserts **one** element right before `</body>` (or at the end, if there's no `</body>`):
  - a fixed bar at the bottom of the viewport with the text "Preview, not published. Upgrade to publish and download."
  - plain HTML + inline `style` only. **No script, no external URL, no class names the page could restyle.** Use a high `z-index` and `all: initial`, or explicit font, colour and size.
  - it must carry the `data-shipfolio-watermark` attribute.
- `export function stripWatermark(html: string): string` removes any element carrying that attribute. Use a simple, well-tested regex for the exact element you insert. Don't write a general HTML parser.
- The stored HTML in `portfolios.generated_html` **stays clean**. The watermark is only added to responses.

### B2. Apply it
- `GET /api/content` (`src/routes/api/content.ts`): load the app user (`getOrCreateAppUser` in `src/server/users.ts`). If `!hasPaidAccess(appUser)`, return `addWatermark(html)`. Paid users and admins get the clean HTML.
- `POST /api/generate`: the same rule for the `html` in the success response. Save the clean HTML, but return the watermarked copy to free users.
- Don't change the publish route or the Vercel deploy route. They're already behind the paid check.
- `PAYMENTS_ENABLED=false` makes `hasPaidAccess()` return true for everyone, so locally there's no watermark unless payments are on. Keep that behaviour.

### B3. Known limit (don't try to fix it here)
A free user can still read `generated_html` straight from Supabase's REST API, because row-level security in `0001_init.sql` allows it. **Closing that is Handoff 02, which Claude Code is doing.** Don't touch row-level security on `portfolios` in this branch.

### 2. Anything done differently from the spec and why
- **ESLint rule fix in `CinematicHeroVideo.tsx`**: `npm run lint` failed on a pre-existing Next.js ESLint directive (`@next/next/no-img-element`), because Next.js plugins are not installed in this TanStack Start project. Replaced it with a standard JSX comment to ensure `npm run lint` passes cleanly with 0 errors.
- **Re-exports in `src/routes/api/generate.ts`**: Re-exported `cleanString`, `parseLinks`, `MAX_LINK_LENGTH`, and `MAX_LINKS` from `generate.ts` so any existing callers importing from `generate.ts` remain unbroken.
- **RLS Delete Policy Observation**: Followed the handoff spec to the letter by adding only SELECT, INSERT, and UPDATE policies (no DELETE policy) to `0009_portfolio_inputs.sql`. In Postgres RLS, if an authenticated user client issues a DELETE without an RLS delete policy, 0 rows are affected. `POST /api/reset` executes `.from("portfolio_inputs").delete().eq("user_id", user.id)` matching the other delete calls. If remote Supabase execution requires deleting this row via the authenticated user client, a delete policy would need to be added to the migration.
